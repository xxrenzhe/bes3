# Bes3 十轮产品与商业优化审计

> 本文把“继续优化产品”落到可执行产品决策。它不是散点 TODO，也不是一次总纲式审计，而是 10 次独立循环迭代：每一轮都有输入证据、发现、落地改动、验证方式、结果和下一轮输入。

## 成功标准

Bes3 必须被用户和运营者理解为一个“买不买决策引擎”，不是泛评测站、优惠券站或纯 AI 内容站。

北极星链路：

```text
高意图搜索 / 站内意图 -> 商品或场景页 -> 买 / 比 / 等 / 跳过 -> 可审计证据 -> 合规 /go 出站 -> 点击与阻塞回流 -> 后台修复 -> 下一批 pSEO 页面
```

硬约束：

- 定位必须一句话说清：Bes3 用真实评测证据、价格窗口和可佣金商家路径，把复杂商品选择压缩成 buy / compare / wait / skip。
- 用户画像必须围绕高焦虑购买任务，而不是泛流量人群。
- 商业模式必须 buyer-first：联盟转化是收入来源，但不允许改变推荐排序。
- UX 必须首屏先回答“现在该做什么”，再解释方法论。
- 自动化 pSEO 必须由意图、证据、价格、链接健康共同驱动；证据不足就 noindex 或降级。
- 系统架构必须服务闭环修复，而不是只生产页面。

## Round 1 - 产品定位

### Cycle 1 independent iteration - Positioning clarity

输入证据：

- `src/app/page.tsx`
- `src/app/about/page.tsx`
- 本文上一版的集中式 10 维审计

发现：

- 站点已经从 generic best picks 收敛到购买决策，但定位还分散在多个页面，没有可复用的产品契约。

落地改动：

- 新增 `src/lib/product-strategy.ts`，把 Bes3 定义为 `buyer decision engine for hard-to-judge products`。
- 将 positioning contract 暴露给 `/api/open/coverage`，避免页面文案和机器 manifest 各说各话。

验证：

- `npm run product:strategy-gates`
- `npm run planv2:check-business`

结果：

- 产品定位从页面 copy 变成可检查、可复用、可被 open manifest 输出的单一事实源。

下一轮输入：

- 用定位契约继续细化核心用户画像。

当前判断：定位已经从“best picks”收敛到购买决策，但公开叙事还需要反复强调“决策引擎”而不是普通内容站。

决策：

- Bes3 的公开定位是 `Buyer decision engine for hard-to-judge products`。
- 首页、About、Trust、Open Data 必须共同解释同一件事：证据、价格、风险、商家路径共同决定下一步。
- 不再把旧 commerce API、泛搜索、泛评测作为产品中心。

## Round 2 - 用户画像

### Cycle 2 independent iteration - User persona precision

输入证据：

- 首页 persona section
- About 页面 audience copy
- `/api/open/coverage` buyer personas

发现：

- 用户画像不能按泛人群写，必须按购买任务写，否则产品会滑回泛评测/泛导购。

落地改动：

- 在 `src/lib/product-strategy.ts` 中定义 `BUYER_PERSONAS`：Anxious buyer、Comparison buyer、Deal-timing buyer。
- coverage manifest 输出同一组 personas，便于 AI/crawler 理解产品服务对象。

验证：

- `npm run product:strategy-gates`

结果：

- 用户入口从“栏目选择”进一步变成“购买焦虑/比较/等价”三条任务路径。

下一轮输入：

- 将三类画像映射到真实痛点，验证产品是否真的解决需求。

核心用户不是低意图闲逛者，而是已经接近购买、但因为证据冲突或价格不确定而犹豫的人。

三类首要画像：

- Anxious buyer：担心买错，想知道“现在能不能买”。
- Comparison buyer：已有 2-4 个候选，想知道默认赢家和反转条件。
- Deal-timing buyer：认可产品，但需要判断现在买还是等降价。

二级画像：

- Evidence skeptic：不信营销规格，需要看真实评测、引用和风险。
- AI / crawler consumer：通过搜索、AI agent 或 open API 读取机器可验证的结论。
- Operator：在后台修复链接、证据、价格、风险和 pSEO 阻塞。

## Round 3 - 真实痛点

### Cycle 3 independent iteration - Pain-point proof

输入证据：

- `src/lib/hardcore-catalog.ts`
- `src/app/page.tsx`
- `src/app/data/page.tsx`

发现：

- 类目 painpoints 已经存在，但还需要一条产品规则：什么痛点足够真实，值得生成强推荐或 pSEO 页面。

落地改动：

- 在 strategy SSOT 和本文中明确：只有证据、价格、商家路径共同支持时才允许强推荐；弱证据必须降级。
- 将 pain-point proof 与 buy / compare / wait / skip 决策状态绑定，而不是只绑定 SEO 关键词。

验证：

- `npm run product:strategy-gates`
- `npm run product:optimization-gates`

结果：

- 产品痛点从“关键词/类目标签”升级为“可验证的购买阻塞”。

下一轮输入：

- 将痛点转成业务功能系统。

Bes3 必须解决的痛点：

- 商品规格无法回答真实场景表现。
- 评测内容分散，用户无法快速比较证据强度。
- 好价、库存和佣金链接状态与推荐结论割裂。
- 许多 SEO 页面为了收录而给出假确定性。
- 运营者不知道哪些页面有流量但不能转化。

产品承诺：

- 有证据才给强推荐。
- 有价格上下文才说是不是好价。
- 有有效 `/go` 才强化购买 CTA。
- 证据薄、链接坏、价格风险高时必须降级为 compare / wait / research / skip。

## Round 4 - 业务功能

### Cycle 4 independent iteration - Business function map

输入证据：

- `src/lib/purchase-decision.ts`
- `src/lib/hardcore.ts`
- `src/lib/commercial-loop.ts`
- `src/lib/seo-automation.ts`

发现：

- 功能模块已经丰富，但如果不按商业闭环组织，会显得像 feature inventory，而不是产品系统。

落地改动：

- 将当前产品功能归并为五个业务系统：Decision surface、Evidence engine、Price-value engine、Commercial loop、Growth automation。
- 这些系统被记录进 `PRODUCT_OPTIMIZATION_CYCLES`，作为后续架构与运营判断的依据。

验证：

- `npm run planv2:check-business`

结果：

- 业务功能与商业目标对齐：每个模块都服务“可信决策 -> 合规出站 -> 数据回流 -> 修复”。

下一轮输入：

- 将五个业务系统串成系统架构 loop。

当前功能应被组织为五个业务系统：

- Decision surface：首页、分类、商品、review、deal、compare、pSEO 场景页都输出 buy / compare / wait / skip。
- Evidence engine：YouTube / creator evidence、风险、引用、共识评分、反馈纠偏。
- Price-value engine：当前价、历史低价、90 天均价、价格提醒、buy window。
- Commercial loop：affiliate sync、`/go` 出站、merchant click metadata、CTR、修复队列。
- Growth automation：taxonomy、intent mining、scenario pSEO、sitemap、llms.txt、open APIs、indexing。

## Round 5 - 系统架构

### Cycle 5 independent iteration - System architecture loop

输入证据：

- `src/app/api/open/coverage/route.ts`
- `src/app/data/page.tsx`
- `scripts/check-planv2-business-coverage.ts`

发现：

- 公开 data surface 说明了覆盖数量，但没有把“意图如何变成决策、失败如何回到运营”讲成架构闭环。

落地改动：

- 在 `src/lib/product-strategy.ts` 中新增 `ARCHITECTURE_LOOP`。
- `/api/open/coverage` 输出同一 architecture loop。
- `/data` 页面展示面向人的 architecture loop。

验证：

- `npm run product:strategy-gates`
- 本地浏览器检查 `/data`

结果：

- 人和机器都能理解 Bes3 不是内容仓库，而是从意图到修复队列的决策系统。

下一轮输入：

- 用架构 loop 约束盈利模式，避免商业化破坏信任。

架构判断：代码已经具备 PlanV2 闭环，但必须在文档和公开页面中讲清楚“为什么这些模块存在”。

目标架构：

```text
Intent signals -> Taxonomy tags -> Product candidates -> Evidence extraction
-> Consensus + risk -> Price-value -> Purchase decision
-> Public page / open API / schema -> Merchant handoff
-> Decision events + merchant clicks -> Admin repair queue
-> pSEO refresh / indexing / syndication
```

架构原则：

- 数据层支持 SQLite / Postgres，但产品逻辑不能依赖本地手工数据。
- 页面必须 server-render 关键结论，不能只靠客户端组件表达购买判断。
- 公开 API 和 schema 必须与页面可见结论一致。
- 后台不是 CMS，而是商业闭环修复系统。

## Round 6 - 盈利模式

### Cycle 6 independent iteration - Monetization quality

输入证据：

- `src/app/trust/page.tsx`
- `src/app/go/[productId]/route.ts`
- `src/lib/recommendation-quality.ts`

发现：

- 联盟佣金已经披露，但商业模式还必须明确“收入跟随决策，不选择赢家”。

落地改动：

- 在 strategy SSOT 中新增 `BUSINESS_MODEL`，包含 primaryRevenue、rankingPolicy、conversionRequirement。
- coverage manifest 输出 buyer-first affiliate model 和 commission-blind policy。

验证：

- `npm run product:strategy-gates`
- `npm run product:optimization-gates`

结果：

- 盈利模式更清晰：可赚钱，但不能用佣金污染排序；强购买 CTA 需要证据、价格、风险和 `/go` 同时满足。

下一轮输入：

- 检查 UX 是否把这种商业模式变成用户可理解的首屏决策。

主要收入：联盟佣金。

可扩展收入：

- Price alert 或 buying assistant 的订阅提醒。
- B2B open commerce / evidence API。
- 品类研究报告或数据授权。
- 商家质量改进反馈，但不得购买排序。

红线：

- 佣金率不参与公共推荐排序。
- 无有效佣金链接不能显示强购买 CTA。
- 有商业出站必须明确 disclosure。
- 推荐结论必须能被证据、价格和风险解释。

## Round 7 - 用户体验

### Cycle 7 independent iteration - User experience clarity

输入证据：

- `src/app/page.tsx`
- `src/components/commerce/PurchaseDecisionCard.tsx`
- `docs/planv2/14.Bes3 主动产品优化与转化门禁机制 (Proactive Product Optimization & Conversion Gates).md`

发现：

- UX 目标不能是“解释更多”，而是让用户先得到下一步，再决定是否深读方法论。

落地改动：

- 将 UX 规则写入 strategy cycle：高意图页面先回答 buy / compare / wait / skip。
- 保持 `product:optimization-gates` 对首屏 CTA、断点、链接语义、移动 sticky CTA 的约束。

验证：

- `npm run product:optimization-gates`
- 本地浏览器检查 `/`

结果：

- UX 质量被定义为“首屏决策清晰 + CTA 语义安全”，而不是页面内容量。

下一轮输入：

- 把同样质量规则应用到自动化 pSEO。

UX 标准：先行动，后解释。

每个高意图页面首屏必须尽量回答：

- 现在买、比较、等价、还是跳过？
- 为什么？
- 价格 / 证据 / 风险信心如何？
- 下一步点哪里？
- 如果不买，替代路径是什么？

移动端原则：

- CTA 必须是 44px 以上可点击目标。
- sticky CTA 不能遮挡底部内容。
- 方法论、开放 JSON、完整证据矩阵不得压过主决策。

## Round 8 - 自动化 pSEO

### Cycle 8 independent iteration - Automated pSEO quality

输入证据：

- `src/lib/pseo.ts`
- `src/lib/seo-automation.ts`
- `src/app/[category]/[landing]/page.tsx`
- `scripts/check-pseo-recommendation-quality.ts`

发现：

- pSEO 的风险是“批量生成页面但没有决策质量”，必须把 indexability 和证据/价格/商家路径绑定。

落地改动：

- 在 strategy SSOT 中新增 `PSEO_AUTOMATION_LOOP`。
- `/api/open/coverage` 输出 pSEO automation loop。
- `product:strategy-gates` 检查 pSEO loop 存在。

验证：

- `npm run pseo:check-recommendation-quality`
- `npm run planv2:check-business`

结果：

- pSEO 被定义为 evidence-backed decision automation，而不是内容工厂。

下一轮输入：

- 将 pSEO 和商业页面的失败原因接入运营修复优先级。

pSEO 的价值不是批量生成页面，而是把长尾问题映射到可验证决策。

索引前必须满足：

- 有足够 eligible products。
- 有独立证据来源。
- 有价格和商家路径。
- 有 FAQ / schema / open payload。
- 有质量边界；证据不足必须 noindex 或明确 researching。

自动化循环：

```text
Search/log/import signals -> pending taxonomy tags -> promoted intents
-> scenario/value pSEO pages -> render audit -> indexing/syndication
-> impressions/clicks/merchant exits -> admin repair queue
```

## Round 9 - 运营与风控

### Cycle 9 independent iteration - Operations and risk feedback

输入证据：

- `src/app/admin/page.tsx`
- `src/lib/admin-blueprint.ts`
- `src/lib/pipeline.ts`
- `src/components/admin/RiskConsole.tsx`

发现：

- 后台不是 CMS，应该优先修复阻碍可信转化的问题。

落地改动：

- 在 strategy cycle 中明确运营优先级：no CTA、no affiliate link、broken `/go`、weak evidence、overpriced CTA、pSEO blocks。
- 保持 PlanV2 business coverage 对商业风险、repair queue、buy-ready metrics 的校验。

验证：

- `npm run planv2:check-business`

结果：

- 运营目标从“发更多页”收敛为“提高可信 buy-ready 页面占比”。

下一轮输入：

- 将前九轮变成可重复执行的治理门禁。

运营目标不是“发更多页”，而是提高可转化且可信的页面占比。

后台必须优先暴露：

- Buy-ready products。
- High-intent pages with no CTA。
- High-score products with no affiliate link。
- Broken `/go` or non-commissionable paths。
- Weak evidence buy CTAs。
- Overpriced or out-of-stock buy CTAs。
- pSEO pages blocked by evidence, price, link, or quality gates。

## Round 10 - 下一阶段产品策略

### Cycle 10 independent iteration - Governance and repeatability

输入证据：

- `scripts/check-product-strategy-gates.ts`
- `scripts/preflight-release.sh`
- `package.json`

发现：

- 上一次回复的问题正在这里暴露：只有 10 个维度不等于 10 次独立循环，必须让 gate 检查循环结构本身。

落地改动：

- `product:strategy-gates` 现在检查 `src/lib/product-strategy.ts` 必须正好有 10 个唯一 cycle。
- 每个 cycle 必须包含 `focus`、`inputEvidence`、`finding`、`landedChange`、`verification`、`outcome`、`nextCycleInput`。
- `/api/open/coverage` 输出完整 `optimizationCycles`，让外部也能看到 10 次独立循环。

验证：

- `npm run product:strategy-gates`
- `npm run type-check`
- `npm run lint`

结果：

- 10 次独立循环从口头承诺变成 release artifact 和可执行门禁。

下一轮输入：

- 未来继续优化时，应从最弱的已验证 cycle 开始，而不是重新写一份大而全策略。

短期聚焦：

- 明确 public positioning：所有核心入口都说“买 / 比 / 等 / 跳过”。
- 强化 persona pathway：用户按任务进入，而不是按站点栏目猜。
- 让 Trust / Data 页面解释商业闭环和 pSEO 质量门禁。
- 把 strategy gate 纳入 release preflight。

中期聚焦：

- 增加意图级漏斗看板：scenario view -> decision view -> merchant exit。
- 增加页面级 pSEO reason codes：why indexable / why noindex。
- 增加 persona-based onboarding：anxious buyer、comparison buyer、deal-timing buyer。
- 对高价值品类做更严格的 evidence source diversity。

长期聚焦：

- 从 affiliate site 演进为 machine-readable commerce decision network。
- 对 AI agents 输出可验证 open commerce objects。
- 对人类用户保持快速、透明、少废话的购买决策体验。

## 本轮落地项

- 新增 strategy gate：`npm run product:strategy-gates`。
- 将 strategy gate 放入 release preflight，防止定位和商业闭环叙事退化。
- 首页强化 persona / pain / commercial-loop copy。
- About 强化目标用户、非目标用户和产品承诺。
- Trust 强化 buyer-first affiliate model、commission-blind ranking、pSEO index gate。
- Open Data / coverage manifest 强化 architecture loop 和 pSEO automation loop。
